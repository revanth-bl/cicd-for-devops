# Notes

## What is a Jenkinsfile?

A **Jenkinsfile** is a text file that defines an entire Jenkins Pipeline using **Groovy-based Declarative or Scripted syntax**.

It allows CI/CD workflows to be stored in version control alongside application source code.

This practice is known as **Pipeline as Code**.

---

# Why Use a Jenkinsfile?

Without a Jenkinsfile:

- Pipeline configuration is stored in Jenkins.
- Difficult to track changes.
- Hard to reproduce pipelines.
- Limited collaboration.

With a Jenkinsfile:

- Stored in Git.
- Easy to review.
- Version controlled.
- Portable.
- Repeatable.
- Production-ready.

---

# Jenkinsfile Location

A Jenkinsfile should be stored in the root directory of the project.

Example:

```text
project/
│
├── src/
├── tests/
├── Dockerfile
├── pom.xml
└── Jenkinsfile
```

---

# Jenkinsfile Workflow

```text
Developer
```

# Pipeline Types

Jenkins supports two pipeline styles.

## Declarative Pipeline

Characteristics:

- Simple syntax
- Structured format
- Easier to maintain
- Recommended for most projects

Example:

```groovy
pipeline {

}
```

---

## Scripted Pipeline

Characteristics:

- Written entirely in Groovy
- Highly flexible
- More complex
- Better suited for advanced workflows

Example:

```groovy
node {

}
```

---

# Main Jenkinsfile Sections

A Declarative Jenkinsfile contains:

```text
pipeline
    agent
    environment
    tools
    options
    parameters
    stages
    post
```

Each section serves a specific purpose.

---

# Pipeline Directive

The `pipeline` block is the root element.

Everything inside the Jenkinsfile is defined within this block.

---

# Agent

The `agent` specifies where the pipeline runs.

Examples:

- any
- specific node
- Docker container
- Kubernetes Pod

Example:

```groovy
agent any
```

---

# Environment

The `environment` block defines variables used throughout the pipeline.

Example:

```groovy
environment {
    APP_NAME = "DemoApp"
}
```

Benefits:

- Reusable values
- Easier maintenance
- Cleaner pipeline code

---

# Tools

The `tools` section configures software used during builds.

Common tools:

- JDK
- Maven
- Gradle
- NodeJS

Example:

```groovy
tools {
    jdk 'JDK17'
}
```

---

# Options

Pipeline options modify execution behavior.

Examples:

- timeout
- retry
- timestamps
- disableConcurrentBuilds

These improve reliability and readability.

---

# Parameters

Parameters allow users to provide input before a pipeline starts.

Common parameter types:

- String
- Boolean
- Choice
- Password
- File

Example:

```groovy
parameters {
    string(name: 'VERSION')
}
```

---

# Stages

Stages divide the pipeline into logical phases.

Typical stages:

- Checkout
- Build
- Test
- Package
- Deploy

Example:

```groovy
stage('Build')
```

---

# Steps

Steps define the actual work performed inside a stage.

Examples:

Linux

```groovy
sh 'pwd'
```

Windows

```groovy
bat 'dir'
```

Echo message

```groovy
echo 'Hello'
```

---

# When

The `when` directive controls whether a stage should execute.

Example:

```groovy
when {
    branch 'main'
}
```

Useful for:

- Branch-based deployments
- Production releases
- Conditional testing

---

# Post

The `post` section executes after pipeline completion.

Common conditions:

- always
- success
- failure
- unstable
- aborted

Typical uses:

- Notifications
- Cleanup
- Artifact publishing
- Logging

---

# Parallel Execution

Multiple stages can execute simultaneously.

Example:

```text
              Test
             /    \
     Unit Test   Integration Test
             \    /
            Continue
```

Benefits:

- Faster builds
- Better resource utilization

---

# Workspace

Each pipeline has its own workspace.

The workspace stores:

- Source code
- Build artifacts
- Temporary files
- Reports

---

# Console Output

Console Output displays logs generated by every stage.

Used for:

- Debugging
- Monitoring
- Troubleshooting

---

# Build Status

Possible pipeline results:

| Status | Description |
|----------|-------------|
| Success | Pipeline completed successfully |
| Failed | One or more stages failed |
| Unstable | Tests failed but pipeline completed |
| Aborted | Pipeline stopped manually |

---

# Declarative vs Scripted Pipeline

| Feature | Declarative | Scripted |
|----------|-------------|-----------|
| Syntax | Simple | Advanced |
| Learning Curve | Easy | Steep |
| Flexibility | Moderate | High |
| Recommended | Yes | Advanced Use Cases |

---

# Best Practices

- Store the Jenkinsfile in the repository root.
- Use Declarative Pipelines whenever possible.
- Keep stages small and focused.
- Use meaningful stage names.
- Store secrets in Jenkins Credentials.
- Avoid hardcoding values.
- Validate pipeline syntax before committing.
- Keep the Jenkinsfile readable and modular.

# Interview Questions

### What is a Jenkinsfile?

A Jenkinsfile is a text file that defines a Jenkins Pipeline using Pipeline as Code.

---

### Why should the Jenkinsfile be stored in Git?

It enables version control, collaboration, change tracking, and reproducible CI/CD workflows.

---

### What is the difference between Declarative and Scripted Pipelines?

Declarative Pipelines use a structured syntax and are easier to maintain, while Scripted Pipelines provide greater flexibility through Groovy scripting.

---

### What is the purpose of the `agent` directive?

The `agent` directive specifies where the pipeline or stage should execute.

---

### What is the purpose of the `post` section?

The `post` section defines actions that run after the pipeline finishes, such as cleanup, notifications, or artifact archiving.

---

# Key Takeaways

- A **Jenkinsfile** is the foundation of **Pipeline as Code**.
- It is stored in the project's Git repository and version-controlled alongside the source code.
- Declarative Pipelines are recommended for most CI/CD workflows.
- Organizing pipelines into clear stages improves readability, maintenance, and troubleshooting.
- A well-structured Jenkinsfile is essential for building scalable, production-ready DevOps pipelines.
